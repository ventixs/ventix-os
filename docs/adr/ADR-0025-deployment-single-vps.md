# ADR-0025: Deployment topology — single VPS for Phase 1

- **Status:** Ratified
- **Date:** 2026-05-09
- **Relates to:** ADR-0007 (no Docker in Phase 0 — relaxed here for Phase 1), ADR-0024 (Auth)

## Context

Phase 1 introduces a backend (Quarkus gateway), Keycloak, Postgres, and a static plugin CDN. We need a deployment posture that:

- Costs near-zero while we validate product-market fit with the first 10–50 tenants.
- Has no vendor lock-in; we can rehost to any other provider with minimal effort.
- Is operable by one person without a Kubernetes background.
- Supports zero-downtime plugin updates (the core promise of MF).

## Decision

**Single VPS, `docker compose`, Caddy reverse proxy, all in one repo.** Concretely:

```
/opt/ventix/
├── docker-compose.yml           orchestrates all services
├── Caddyfile                    HTTPS + reverse proxy + static file serving
├── .env                         secrets (gitignored; deployed via secret manager)
├── plugins/                     static plugin bundles, served by Caddy
│   ├── com.ventix.almacen/1.2.3/...
│   └── ...
├── shell-dist/                  built shell, served by Caddy
└── data/
    ├── postgres/                postgres volume
    └── keycloak/                keycloak volume
```

Services in compose:

| Service | Image | Memory | Notes |
|---|---|---|---|
| `caddy` | `caddy:2` | ~50 MB | TLS + proxy + static |
| `postgres` | `postgres:16` | ~150 MB | Single DB, schemas per concern |
| `keycloak` | `quay.io/keycloak/keycloak:25` | ~400 MB | start-dev for now, prod mode later |
| `gateway` | local Quarkus build | ~250 MB native (~80 MB) | `/api/*` |

Total: ~850 MB RAM minimum. Recommended VPS: **Hetzner CX22 (4 GB RAM, ~€4/mo)** for headroom.

## Hostname Layout

```
ventix.tu-dominio.com           → /opt/ventix/shell-dist     (Caddy static)
plugins.ventix.tu-dominio.com   → /opt/ventix/plugins        (Caddy static, immutable cache)
api.ventix.tu-dominio.com       → gateway:8080                (Caddy reverse_proxy)
auth.ventix.tu-dominio.com      → keycloak:8080               (Caddy reverse_proxy)
```

Caddy auto-provisions Let's Encrypt certs. Configuration is ~30 lines.

## Plugin Deployment

A plugin's CI:

1. `pnpm build` → `dist/` containing `remoteEntry.js` + chunks + `manifest.json`.
2. `rsync` (or `scp`) to `vps:/opt/ventix/plugins/<id>/<version>/`.
3. POST to `api.ventix...` registering the version in `plugin_versions` (RFC-0011).
4. Optionally PATCH active tenants to bump them to the new version.

No container rebuild. No restart. The new bundle is just files Caddy already serves.

**Cache headers** (set by Caddy):

```
plugins.ventix.../<id>/<version>/* → Cache-Control: public, max-age=31536000, immutable
```

Versioned URLs are immutable; if you change the bundle, you change the URL. Browser cache is your friend.

## Backups

- **Postgres**: nightly `pg_dump` to off-VPS object storage (Backblaze B2 / Hetzner Object Storage). 30-day retention.
- **Keycloak**: same — its data is in Postgres; or use `kc.sh export` for realm exports.
- **Plugin bundles**: rebuildable from source, no backup strategy needed.
- **VPS snapshot**: weekly via the provider, in case the host disk dies.

Recovery objective for Phase 1: **RTO 4h, RPO 24h.** Stricter posture is Phase 1.5+.

## Observability (Phase 1, minimal)

- `caddy` logs → file, rotated weekly.
- `gateway` logs → JSON to stdout, captured by docker.
- One health-check endpoint per service, polled by an external uptime monitor (Uptime Kuma self-hosted or BetterStack free tier).

Full Prometheus/Grafana/Loki stack is Phase 2; not justified at this scale.

## Security Posture

- SSH: key-only, fail2ban enabled.
- Firewall: 80, 443 inbound only. Postgres/Keycloak/gateway never exposed to the public internet — only to Caddy via the docker network.
- Secrets: `.env` file with restrictive permissions, generated by an `infra/setup.sh` script. Do **not** commit secrets; commit `.env.example`.
- Keycloak `start-dev` is for local only. Production uses `start --optimized` with proper hostname/HTTPS settings.
- Plugin bundles served from a separate hostname so `Content-Security-Policy` on the shell can lock origins.

## When to Outgrow This

Move to a multi-VPS / managed services posture when **any** of these is consistently true for two months:

- Average RAM utilization > 70 % during peak hours.
- p95 API latency > 300 ms.
- More than ~100 tenants with regular activity.
- A single outage of >1 hour costs more than the migration cost (~1 week of work).

The migration target is documented in a future ADR. Not now.

## Consequences

**Positive:**
- Cheap. A €4/mo VPS runs Phase 1 comfortably.
- Operable by one person. No Kubernetes, no Helm, no cluster admin.
- Portable. The whole stack is a `docker compose up` away on any other host.
- Aligned with the "simple until it hurts" rule.

**Negative:**
- Single point of failure. If the VPS dies, everything dies. Mitigated by snapshots + off-VPS DB backups.
- Vertical scaling only. Hitting CPU limits = upgrade VPS, not horizontal scale.
- No HA. Maintenance windows show as downtime. Acceptable at our scale.

## What This Does NOT Decide

- The CDN strategy when we move plugins off the VPS to Cloudflare R2 / S3 (future).
- The CI runner posture (we currently use GitHub Actions; that's orthogonal).
- The DR plan beyond simple backups (Phase 1.5).
